# 改动记录 2026-11-10 吊舱 RGB 帧不再计算 dx/dy（POD_MM=false）

## 现象
统一零位基准后，同一时刻：
- 板端双目（深度相机）真值：dx=20 dy=-6
- App 双目帧：dx=20 dy=-8  ✅ 与板端一致
- App 吊舱 RGB 帧：dx=-8 dy=-8  ❌ 方向都反了，差 28mm

## 原因（不是标定常数没更新）
吊舱 REF(642.8,361.4)/1.19mm·px⁻¹ 本身是对的：零位那 8 帧里吊舱与双目**同帧**实测，毫米层面 1:1
（归零后双目 0.0±0.6mm、吊舱 0.0±1.9mm）。但现在吊舱算出来是 **负**的，说明吊舱画面里的四孔
**已经到了基准点的另一侧**（中心 649.5 > 参考 642.8），而双目画面里四孔明显在基准左边（761.8 < 786.0）。

两台相机装在同一个云台平台上、看同一个目标，mm 误差不可能一正一负。能同时解释「位置反了」的只有：
1. 吊舱云台角度变了（吊舱画幅整体平移，参考点失效）；
2. 吊舱光学变焦变了（mm/px 与参考点同时按画面中心缩放，两套常量一起失效）。

零位标定只在“云台锁在零位角度 + 变焦锁死”这一个姿态下成立。现场只要动过云台或变焦，吊舱算出的
mm 就是错的，而且**没法靠改常数修**——必须重标该姿态，飞手一操作又废。

结论：吊舱帧不能作为 mm 来源。板端纠偏本来就只用深度相机那一路，吊舱只是画面好看/看得远。

## 改法（App：gimbal_compare.html）
1. 新增开关 `const POD_MM = false;`（常量区，带注释说明怎么恢复）
2. `recompute()`：`frameSrc!=='stereo' && !POD_MM` 时 → 四个 mm 格全显示 `—`，`lastDx/lastDy=null`，
   不发布 MQTT；**保留** 板心像素 `vscenter` 显示与圆的标注/检测
3. 发布条件加严：`calibrated && frameSrc==='stereo'` —— 吊舱帧的 mm 永不出门
4. `calibrate()`：吊舱帧不再改写吊舱基准（写了也没人用），但**保留触发板端二次校准**的通道
   （板端用自己的深度相机值，不读吊舱帧，这条命令本身安全），提示文案改为“已触发板端二次校准…参考点未改”
5. UI：`POD_MM=false` 时启动即隐藏「吊舱dx/吊舱dy」两格，避免常显 `—` 像坏了；换算依据说明段重写
6. 取帧提示：吊舱帧提示“只用于看图/标注，纠偏值统一看双目帧”

恢复条件（写进注释）：云台锁到零位角度、变焦锁死 → 重跑零位同帧标定 → `POD_MM=true` 并重校 REF_X/REF_Y。

## 验证（node pod_off_chk.js，用 HTML 里抽出的真实 recompute/calibrate 跑）
| 场景 | 结果 |
|---|---|
| script 块语法 | 1 块，0 错误 |
| A 吊舱帧 4 孔 | 4 格均 `—`，`lastDx/lastDy=null`，发布 0 条 |
| B 同帧强制 POD_MM=true（旧行为） | `-8 / -9` —— 精确复现现场 `-8/-8`，证明现场值就是吊舱基准失配造成的 |
| C 双目帧（1536 口径还原后中心 761.8,567.4） | `20.2 / -6.2`，发布 `{"dx":20.17,"dy":-6.19}` |
| D 吊舱帧点「校准」 | 只发 `aruco/stop {"cmd":"calibrate"}` 1 条，基准未改（642.8/361.4、786/560 均不变） |
| E 双目帧点「校准」 | 本地保存基准，不发任何命令（原行为不变） |

## 影响面
- 板端：**无改动**，不用重编、不用重启。
- App：HTML asset 改动，需重新打包安装到 G20 才生效。
- 手动标注回传（`aruco/manual/resp`）走的是板端深度相机帧，不受本次改动影响。
